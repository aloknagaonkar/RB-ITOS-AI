# Closed recovery integration — exact-plan maintenance

Default command: `.venv/bin/python hilega-recovery-install-v1/manage.py --repo "$PWD"`. Default is read-only with respect to live application state: it runs the current 10-case closed review, six plan tests, two native pause-recovery scenarios on new synthetic databases, unit syntax verification, and emits PLAN.json plus SHA and CHECK-VALIDATION.json. No services are controlled, live recovery installed, or backups created during check.

The generated plan describes nine new files: immutable recovery code/config, one user oneshot recovery service, and one dependency drop-in for each of six application services. Recovery verifies the closed bundle, wrapper, installed runtime payloads, persistent preparation route and hard order gate, then invokes native pause. It never arms, reads broker credentials, provisions authority, enrolls ownership, or sends orders. RemainAfterExit allows all six units to require successful recovery before starting. Subsequent worker restart also retains its existing native startup pause. No scheduled live window is created.

After reviewing the exact plan, apply with `--action apply --plan /absolute/PLAN.json --approve-plan-sha256 SHA`. Apply expires 30 minutes after check and requires unchanged controller version/session, configuration bindings and absent destinations. It holds the shared closed-rollout maintenance lock and uses pinned native Group 1 hold/start functions. All six services are stopped. Both databases receive consistent SQLite backups with full integrity checks; installed code, wrapper and original approval/configuration bindings receive private byte-preserving backups. Files are installed, the user manager reloaded, recovery executed, and the original closed runtime restarted. Controller remains paused.

`--action status` verifies exact installed files and the closed runtime. `--action rollback` stops the six services, removes only exact files created by this plan, reloads, and restarts the original closed runtime. Databases are NEVER restored automatically; cursors are not rewound. An unexpected apply failure leaves services stopped for inspection/rollback. The new persistent recovery is pinned to this CLOSED, factory-disabled bundle: future runtime/factory changes need a new recovery binding review.

Maintenance changes application startup dependencies and creates a user service; it does not alter existing unit fragments, supervisor approvals, environment files, original installed runtime source, or the execution gate. No actual VM reboot is requested or certified. Prior Package A results are reused; the full repository regression is not rerun. All behavioral checks are VM-only. Local verification is syntax/archive only.
