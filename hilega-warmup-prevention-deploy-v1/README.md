# Coordinated warmup prevention deployment and milestone update

Default action check prepares a successor exact plan without changing live sources/services/cache. Requires the active predecessor plan and exact four-file proposal hashes. Runs six transaction tests on VM (complete apply/restore, interruption after each of the first three replacements, rejection of external edits, changed-payload rejection). Verifies the prior six-case binding proposal receipt and exact candidate sources; prior 18 writer cases are reused, not reexecuted. Independently calls native inspect_warmup(repair=False), checks current runtime health before/after, stages payloads and records all original/new bindings. Produces PLAN.json, CHECK-VALIDATION.json and MILESTONES.md. Apply expires after 30 minutes.

Apply requires the new plan SHA. Acquires the shared maintenance lock. Requires paused controller, empty closed lifecycle baseline and no active quote-observer unit. Stops all six managed services and the recovery oneshot, verifies quiescence, backs up four original files and both database files without SQL mutations. Installs the writer plus manifest, CLI and companion pins together. Checks the installed package, starts recovery and services, verifies native heartbeat/empty baseline, independently recomputes historical warmup and records installed status. No original active plan or immutable release is edited. No controller resume, authority activation, broker reads by this tool or orders. Existing services may perform their usual broker reads after restart.

Post-install use THIS tool's --action status --plan <new PLAN.json> --approve-plan-sha256 <new SHA>. It has explicit successor model HILEGA_WARMUP_PREVENTION_INSTALL_V1; the old registration rollout CLI does not accept this plan. New identity readers can use its destination, release_sha256, application_db and adapter_db fields, but older read-check packages hard-code the predecessor status driver and must not be pointed blindly at the successor. MILESTONES.md records tested, staged and deployed evidence separately. It is a local milestone file, not a GitHub milestone update.

Rollback uses this tool --action rollback with the same plan/hash. Stops services, requires the empty closed baseline, restores exact original SOURCE/CONFIG files only and restarts/health-checks. It never restores databases or rewinds the source cursor. If apply fails after backups and installation begins, services are stopped and a recoverable failure phase recorded; explicit rollback is supported from those failure phases. External file edits block automatic source restoration. Failures during early quiesce or backup require inspection before retry. No automatic DB rollback or unconditional retry.

No startup/crash/reboot rehearsal is claimed for this four-file maintenance plan. The writer's behavior and hash chain have prior VM validation; the six new file-transaction cases do not prove service startup. Actual managed restart and warmup checks occur during approved apply, with original-source recovery available. A failed later check may leave files installed and services stopped. Inspect TRANSACTION.json and audit records.

Warmup before/after is independently recomputed from existing historical caches using repair=False, without synthetic candles. It may expose another incomplete historical cache and block maintenance. Successful prevention means only complete nonempty operational warmup writes through this writer; upstream outages, holidays, other direct writers and unmanaged processes are outside that guarantee. Empty existing caches cannot be overwritten by empty refreshes. No trading policy changes.

Local validation: Python syntax, AST and ZIP integrity only. Tests execute on the VM. WebSocket/quote validation remains a separate open-session requirement.
