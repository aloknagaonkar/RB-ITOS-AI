# Combined trust files, candidate issuer, worker registration and recovery batch

Default check runs 16 new private-file/worker tests plus one synthetic seed preflight, two actual native startup pause scenarios on disposable databases, exact new recovery-binding scenarios, and managed default-worker startup/restart. It creates a sealed candidate with the new code and an exact 30-minute closed-upgrade plan. No live root/key/grant/context is generated, no application service is changed by check, and no broker read is performed. Earlier 22 authority tests are reused, not rerun. All behavioral work runs on the user VM.

New code provides pinned private registry/key/grant readers (owner-only parent/file permissions, hashes, no symlinks or hard links), a candidate-only HMAC issuer function, and a registration adapter that composes the existing verified private context/factory adapter. Registry/root rotation invalidates cached operation rather than silently changing identities. A registered restart verifies pause before attaching. Missing adapter databases or incomplete schema are rejected; an admitted synthetic candidate may only reopen an existing complete canonical Store. No owner enrollment is implicit.

The candidate worker's ClosedRegistration.poll delegates through a manifest-bound FACTORY-REGISTRATION.json. The staged config is enabled=false with every private pointer null. Its default behavior remains the prior closed preparation worker. The outer release and preparation dependency manifests bind the new code/config. The existing execution gate and one-position/no-monetary-caps policy remain unchanged.

Enabled registration is a Python/synthetic candidate path only. Managed tests certify the disabled default, not a configured live factory. An actual approved issuer/root, scoped signed grant, private context and owner must still be provisioned and reviewed; enabled worker heartbeat/source integration and configured boot recovery need qualification before any live deployment. This package does not open the hard gate or provide production execution permission. Do not edit enabled or any sealed file in place.

After a passing check, exact --action apply/status/rollback use the generated --plan and --approve-plan-sha256, with the same closed transactional engine already validated on the VM. Apply stops six application services, makes verified private code/config/database backups, installs the sealed candidate and matching wrapper/recovery binding, then restarts and checks the paused empty baseline. Rollback restores the current predecessor release, never databases or source cursors; it preserves new immutable artifacts. After apply use this package's status, not predecessor tools bound to the old wrapper. Failures hold services stopped for explicit reviewed rollback. No automatic failed-transaction retry is provided.

The package updates MILESTONES.md from the latest 22-case candidate checklist and records code/test/deployment separately. Candidate issuer code is not a provisioned production authority. Full repository regression, market evidence, fees, actual owner enrollment, VM reboot and final activation remain pending. Local checks are Python syntax, ZIP CRC and unchanged transaction-function AST comparison only.

V2 corrects the predecessor status-tool selection: the active policy release is checked with hilega-position-policy-upgrade-v1, not the older Group 2 upgrade tool. --reuse-passed-review searches existing completed review folders and accepts only identical sealed candidate bytes, matching authority/source bindings, two successful JUnit/process receipts (16+1 cases) and the two-scenario native startup receipt. Their hashes are carried into the new plan bindings. It does not skip the still-required managed/default-worker and exact recovery-binding checks. No live services are changed during check.
